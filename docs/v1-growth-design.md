# V1.0 资源成长设计与原生机制调查

调查基线为本机 Terraria 1.4.4.9／tModLoader 2026.9.3.1 的程序集及项目提交 `a7fe76a`。按 [V1.0 规格](requirements-v1.0.md) 推进。实机结果在 [验收清单](acceptance-checklist.md) 记录。

## B01 与 B02 采集

`/tpamp goal 帮我收集 10 个木材` 由现有多人目标入口识别。一个目标使用同一个服务器任务身份，绑定世界会话、AI 代次、控制者、宿主会话和停止版本。Python 宿主维持原有心跳，实时的搜索、移动、挥斧和拾取由 C# 负责。采集期间不发布模型动作邮箱，跟随、自卫和短目标服从同一套停止及替换规则。没有新调度框架。

- 搜索以 AI 当前位置为中心，横向 24 格，纵向脚底上 5 格至下 3 格，并限制目标在任务起点左右 48 格内。第一条路线面向草地下的普通森林树，排除侧根、非底部树干、失效或受保护方块。复用原生水平导航、近距跨坎、物品范围和视线检查。
- 从 AI 自有背包选择普通挥动斧。通过 `Player.ItemCheck_Inner → ItemCheck_OwnerOnlyCode → ItemCheck_UseMiningTools → ItemCheck_UseMiningTools_ActuallyUseMiningTool`。最后一步原生处理斧力、命中累积、`WorldGen.CanKillTile`、`KillTile` 和掉落。只在受控服务器角色执行本任务时开启原生归属门控。树干移除后发送局部原生 tile square，地面掉落和拾取走正常物品机制。
- 原生工具调用栈中的树木掉落带有 `EntitySource_TileBreak`。用物品对象和实际地面转移追踪木材。原生拾取前后核对世界剩余与背包变化，连续拾取同一混合叠堆时保留剩余归因，整叠入包只累计其中的任务木材。多个地面堆之间部分转移、外部修改或物品对象无法对账时，进度可能偏低。
- 保留已拾取的正常物品。最多尝试 16 棵树，任务最长 120 模拟秒，单树砍伐至多 10 秒，并有限等待掉落可达和入包。失败、死亡、宿主会话变化、停止或替换都会结束任务。按任务 ID 记录尝试、掉落及增量，状态快照可读当前或上一条采集结果。

暂未覆盖掌树、雪地树及其他木材类型、地下与多层寻路、地图视野系统或复杂混合意图。局部扫描会读取候选瓦片，实际砍伐前必须再次满足无遮挡和原生距离。真人可以正常拾取掉落。任务不会锁住掉落物。

## B03 基础制作调查

### 已核实

- 本机 `Recipe.SetupRecipes` 中，木剑为 `WoodenSword = 24`，消耗 7 个普通木材（`Wood = 9`），制作站为 `WorkBenches = 18`。正式实现应查 `Main.recipe` 中启用的注册配方，检查配方被模组更改、禁用或附加条件的情况。
- `Player.AdjTiles()` 按玩家位置建立相邻制作站及液体条件，还可能调用依赖客户端配方 UI 的 `Recipe.FindRecipes`。真人已经放置的工作台可以作为后续验收的制作站。
- `Main.CraftItem(Recipe)` 调用 `Recipe.Create()` 和 `RecipeLoader.OnCraft`。无参 `Recipe.Create()` 从 `Main.player[Main.myPlayer].inventory` 扣料，还读取本地玩家可用的箱子、虚空袋或模组材料，并刷新客户端配方。成品路径涉及客户端鼠标物品。它不能直接作为任意服务器 `Player` 的交易入口。

配方数据及钩子接口见 [tModLoader Recipe](https://docs.tmodloader.net/docs/stable/class_recipe.html) 和 [RecipeLoader](https://docs.tmodloader.net/docs/stable/class_recipe_loader.html)。

### 实现前置与一致性

优先调查可显式传入 Player 的原生交易路径。若本版本没有可复用入口，再评审一个只支持注册木剑配方的服务器适配。适配必须隔离材料来源、配方可用性和成品落点；在同一服务器更新内重验身份、工作台、材料和入包空间，确定所有受影响槽位。验证原生配方消耗和创建钩子的副作用、成品修饰词和材料回滚，证明失败不会让扣料或产物单独生效。还要覆盖材料分散在多个槽位、目标被替换、背包空间不足，以及真人库存和鼠标物品保持原状。

目前缺少经验证的 Player 参数化制作入口和可回滚的成品落点，B03 停在调查。全局切换 `Main.myPlayer` 或手工扣木再发剑都会越过已确认的隔离／原生规则边界。

## B04 装备成长调查

`DemoPlayerSystem.SelectItem` 可选择现有库存槽位。单人原型已使用 `WoodenSword`，多人直接挥砍路径当前只开放铁阔剑。后续先从正常制作结果确认木剑进入 AI 背包，再核对 `Swing`、直接近战和无射弹条件，把木剑接入同一原生挥砍、命中框和冷却路径。验收依据为指定槽位、当前攻击序号、木剑类型、目标及原生 `item-hit`。B04 等 B03 得到可靠原生制作品，当前保留现有武器范围。

## B05 持久化预研

| 事项 | 推荐设计 |
| --- | --- |
| 角色身份 | 首次正常生成分配 AI GUID。虚拟槽位和 ActorGeneration 只用于运行时隔离。稳定角色身份进入存档 |
| 所属世界 | 使用 `Main.ActiveWorldFileData.UniqueId`，区分运行时 `WorldSession.Id`。V1 默认世界绑定，世界副本应按同一个档案的分支处理，禁止默认带装备跨世界 |
| 控制者归属 | 单人 Host & Play 档案由宿主明确认领。Player／Socket token 仅验证当前连接；角色昵称或客户端自报 UUID 只能作提示。多人转让和跨世界迁移需要产品确认 |
| 内容与序列化 | 保存版本号、世界／AI GUID、归属、代次、确认保存时间、生命／魔力成长、难度、物品及装备槽位、持有槽。用 tModLoader 的 `PlayerIO.SaveInventory/LoadInventory` 或 `ItemIO.Save/Load` 与 `TagCompound` 保留堆叠、修饰词和 Mod 数据。任务、输入、目标令牌及死亡中的动作不持久化 |
| 保存顺序 | 推荐随世界保存事件生成 AI 内存快照，先停止旧动作，再由保存路径写入版本化数据。退出清理前要先明确保存／放弃结果。避免用世界卸载回调作为唯一保存点，也不要在模型线程拿游戏对象 |
| 恢复顺序 | 校验世界、归属、版本及完整性，先完整还原到未发布 Player，再认领服务器槽位。只有确认不存在旧档案才发起步装备。损坏、缺失 Mod 或未知版本给出可诊断失败，避免把失败读档当作首次生成 |
| 异常退出 | 状态反馈区分内存进度与最近确认存档。恢复之前的有效检查点，已读档旧任务保持待命。世界与 AI 可能跨文件提交，需要测试每个中断顺序，以及材料在 AI、世界箱子、地面之间移转时的重复和丢失风险 |

推荐先评估 `ModSystem.SaveWorldData/LoadWorldData` 与 tModLoader 世界备份的调用顺序，把 AI 状态和世界检查点配对。备选为独立同卷档案：序列化到临时文件、重新读验、刷盘并原子替换，前一有效版本保留为备份。独立档案可保住自身完整性，仍需用世界检查点编号或明确的写入协调解决跨文件一致性。无法确认配对时，不自动把旧角色库存与更新世界拼接。

需要确认三项产品决策：档案由开服者独占还是允许转交；`remove` 仅移除当前角色还是另设明确删除档案入口；异常退出后接受回到最近世界检查点，还是需要跨世界状态一致的更强恢复保障。当前不修改正式存档。序列化参考 [ItemIO](https://docs.tmodloader.net/docs/stable/class_item_i_o.html) 和 [TagCompound](https://docs.tmodloader.net/docs/stable/class_tag_compound.html)。
