# 可复用的开发经验

整理：2026-10-21。用于本项目后续开工前参考；具体测试证据见 [验证记录](validation.md)，当前开发重点见 [TODO](../TODO.md)。这里只保留可以指导下一次行动的经验，不重复记录开发流水账。

## 1. 按用户能体验的场景交付

选择一个小场景，例如“收到跟随命令 → 跟上用户 → 收到停止后停下”，再补齐这个场景缺少的能力。原生攻击、受伤和对象归属等必要机制确认后，尽早接入真实上层调用；不要等所有底层动作都充分测试后才联调。

今天接入模型才暴露“移动还没完成就被攻击替换”。以后应尽早通过真实使用发现接口问题。优先处理使场景无法继续的缺口，例如死亡后不能恢复行动；每批交付一个可用结果，再开始下一批。

## 2. 为检查设置停止条件

本批相关场景跑通、结果有必要依据即可交付。只有修改了共享行为或出现具体风险时，补受影响的少量回归；遇到真实 bug，再记录最小复现、定位、修复并确认问题解决。

已经通过且未受改动影响的项目不反复重测；同一攻击机制选一个代表，不逐把验收武器。测试因失焦等环境原因中断时，保留已取得的结果，只补缺失部分，不把整轮从头再跑作为默认操作。

这不等于省略必要事实：原生伤害归属、是否真的重生、是否走过台阶，仍要有对应结果。重点是取到决定性的证据后就停止扩展检查。

## 3. 先区分产品问题与辅助工具问题

先看游戏是否在运行、当前入口是否响应，以及现有记录能否解释现象。单人游戏失焦会暂停，入口超时不能直接说明控制层坏了；超时后的动作结果可能未知，恢复后先看一次状态，不盲目重放生成等操作。

桌面键盘注入不好用时，已有 JSON 入口足以推进角色开发，就沿用它。需要读取原生实现时，先用本机已有库和工具；不要让安装反编译工具、修复通用自动输入等辅助工作占据功能批次。辅助方案连续受阻时及时换路或报告具体限制。

## 4. 减少整游戏重启，复用原生机制

外部构建遇到 tmod 占用时，下一次必要构建先尝试禁用模组并重载以释放文件，构建后启用并重载；失败再完整重启。这个较短流程有官方文档支持，本项目尚未实测走通，不能写成已验证。不要为尝试重载单独安排多轮实验或提前建设热更新工具链。

文档和外部 Agent／测试脚本变化不需要重启游戏。游戏控制优先让原生移动、碰撞、伤害和重生负责实际行为，只适配额外玩家槽位被跳过的必要路径；不重复调用 Player.Update 或切换 Main.myPlayer 来掩盖问题。版本相关的少量关键分支需要确认，确认后不重复调查。

## 5. 工具要讲清动作的时间语义

“按顺序下发命令”不等于“按顺序完成动作”。当前新动作替换旧动作，同批发移动和攻击，移动不会先自动跑满指定时间。工具说明必须说明是否等待、何时返回，以及结果表示收到请求还是动作已完成。

后续先把当前场景的动作完成和实际反馈做好，让模型少猜帧时序。需要持续跟随时再发展本地持续动作，由模型选目标和策略，控制层连续执行；不要让模型每走一小段都重新推理，也不要提前抽象完整任务框架。仅补提示词是临时改善，不代表执行接口问题已彻底解决。

## 6. 让必要事实支持模型结论

目标掉血可能来自真人或其他 NPC，模型说成功不等于任务成功。工具应直接返回与本次目标有关的动作结果和事件，减少模型反复查状态、猜测归属。

本轮模型误报铁阔剑命中，而事件只有木剑命中。以后缺少对应依据时报告“未确认／未完成”，不能用“事件可能被截断”补出证据。宿主对当前任务需要的少量结果作事实判断即可，不因此建设通用全游戏验收系统。已有原始报告可以用于离线修复和复查，避免为了确认同一个错误反复调用 API。

## 7. 区分测试场景变化和产品默认行为

测试前简短说明会生成什么、是否会死亡，以及结束后角色是否保留；收尾说明当前实际状态。脚本移除测试角色不等于关闭自动重生。当前普通／软核 AI 自动重生默认开启；明确 remove 才取消这个对象，体验演示尽量保留角色方便继续观察。

默认装备和额外测试装备也要分清：普通新角色带铜短剑，今天的铁阔剑是脚本额外发放，不能据此说初始装备已支持。当前两把武器白名单是原型限制，不能说成游戏要求逐把适配。名称和印象不确定时，按当前功能需要查 Wiki 与本机实现，记录必要结论即可。

## 8. 优化和文档投入要服务当前目标

先确认用户接受的时间和调用成本，再决定是否优化。本项目目前单轮约 4 万 tokens 可以接受；先做好指令、行动和跟随，长期上下文优化作为数小时运行前的后续事项。可靠动作减少无效重试，也能顺带减少开销。具体方案见 [上下文开销分析](agent-context-cost.md)，当前未实施压缩。

文档在交付时集中同步：README 放当前能力和入口，TODO 放下一步，validation 放证据，技术设计只在结构／职责改变时更新。其他文档只补确实变化的内容，引用已有记录，避免把同一事实重复写到多处。没有明确复用需求时，不新建技能、框架或测试平台。

## 本次留下的两个具体脚本经验

- PowerShell 变量名不区分大小写：`$Respawn` 开关和 `$respawn` 局部变量会冲突，局部变量使用 `$respawnEvent` 等明确名称。
- 游戏计时的观察以模拟 tick 为准：失焦暂停时，墙钟等待 10 秒不代表原生复活计时已经走完。仅在检查游戏时间相关行为时使用 tick，不要求每个动作都额外做计时测试。

## 下次开工怎么用

先读 README 当前交接和 TODO，再用本文件避免重复绕路。确定一个可体验的小场景及必要检查，复用现有入口完成后就交付；出现具体 bug 再针对处理。结束时集中记录结果、当前边界和下一步，不在收尾继续扩大功能或测试范围。
