# Terraria AI Companion 技术需求说明书

版本：V0.1（技术预研版）
目标平台：Terraria / tModLoader
项目类型：基于大语言模型的自主游戏智能体
当前状态：需求初步明确，关键技术路线待验证
归档日期：2026-10-20

本文件整理自用户提供的需求说明，未将参考项目的能力视为本项目已实现的功能。

## 1. 项目目标

开发一个基于 AI Agent 的 Terraria 智能队友，使其作为具有真实玩家特征的角色，与人类玩家共同探索、采集、建造、制造装备、战斗和推进进度。最终尝试从初始开荒推进至月亮领主。

核心原则：

1. 拥有实际游戏实体。
2. 拥有独立生命值、背包、装备、死亡与复活能力。
3. 遵守正常玩家的资源、战斗和成长规则，不靠生成物资或无敌完成任务。
4. 能接受玩家指令，也有一定自主决策能力。
5. 优先单窗口体验，不强制双客户端。
6. 底层控制与上层 Agent 解耦，允许替换角色实现。
7. 后续支持 2–3 名真人联机，共享同一个 AI 控制角色；第一批仍只验证单人最小演示。

## 2. 技术架构

| 层级 | 技术选择 | 职责 |
| --- | --- | --- |
| 游戏环境 | Terraria + tModLoader | 世界、玩家及游戏机制 |
| 游戏控制层 | C# | 玩家动作、状态读取、任务执行 |
| 通信层 | HTTP / IPC | 连接游戏进程与 AI 服务 |
| 工具层 | MCP Server（计划接入） | 标准化游戏操作工具 |
| 决策层 | Python + LLM | 理解意图、规划、调用工具 |
| 记忆层 | 本地持久化，后续可加入 RAG | 任务、偏好和历史 |

### 方案 A：游戏内虚拟 Player

一个客户端，由 tModLoader 管理独立 Player，C# 执行行为。需验证玩家机制、装备效果、存档和模组兼容。

### 方案 B：独立 AI 客户端

AI 通过独立客户端作为正常联机玩家进入世界，可以在本机、另一台电脑或云电脑运行。需处理控制、自动连接和运行管理。

当前决策：先验证方案 A，保留方案 B，不提前确定云端部署。

## 3. 功能需求

| 编号 | 功能 | 要求 |
| --- | --- | --- |
| FR01 | AI 玩家实体 | 独立名称、位置、生命值、魔力、物品栏和装备栏，能够受伤、死亡、复活 |
| FR02 | 基本角色控制 | 移动、跳跃、平台穿越、使用道具、切换物品、攻击、挖掘、放置；由控制层执行，LLM 不可任意修改内存状态 |
| FR03 | 自然语言指令 | 聊天或专门界面接收跟随、攻击、采集、备战、停止和返回等指令 |
| FR04 | 环境感知 | 结构化读取自身、玩家、敌人、附近方块、可见资源、危险地形、背包和装备，截图不是主要感知方式 |
| FR05 | 自主移动与寻路 | 处理平台、高差和障碍；无法抵达时恢复或报告失败，不无限重试 |
| FR06 | 自主战斗 | 识别和选择敌人、使用装备、依血量和环境调整战术；实时瞄准和闪避由控制算法负责 |
| FR07 | 任务规划与执行 | 拆分子任务、检查结果、重新规划；长期任务可暂停、取消和查询 |
| FR08 | 资源与装备管理 | 正常拾取、整理、使用工具和装备；后续扩展制作和交易 |
| FR09 | 记忆与协作 | 保存任务、位置、历史和偏好，区分同行协作与独立任务，避免未经允许干扰玩家 |
| FR10 | 安全与约束 | 默认无作弊权限，不擅自大规模改建筑、消耗稀有物资或触发关键 Boss；支持紧急停止、超时和异常恢复 |
| FR11 | 多人协作（后续） | 2–3 名真人与 1 个 AI 角色共同联机；各客户端看到同一个 AI，角色状态和行为一致，避免每个客户端各自生成或控制一份 AI |

## 4. 非功能需求

- 性能：实时动作不依赖 LLM 每帧响应；通信和推理不阻塞主循环。
- 可靠性：Agent 断开时停止危险任务，进入安全待机。
- 持久化：正常退出、重新进入后，尽可能正确恢复角色装备、物品和任务状态。
- 兼容性：先指定 tModLoader 稳定版本及原版内容，大型内容模组后续验证。
- 扩展性：MCP 接口与具体控制方式解耦。
- 安全性：外部接口仅授权程序可调用，不开放任意代码执行。

## 5. MVP：第一个可玩版本

必须具备：独立玩家实体、正常生命值/背包/装备、跟随/跳跃/移动、简单指令和自动攻击史莱姆、死亡复活、随时停止或改变行为。

验收场景：在普通测试世界中，与玩家持续探索地表，跟随、战斗、受伤、死亡复活，重新进入后恢复必要角色数据。不要求自主通关。

## 6. 开发阶段

| 阶段 | 交付 |
| --- | --- |
| P0 技术可行性 | 验证玩家实体、输入控制、装备与存档，比较单/双客户端 |
| P1 玩家控制 | 移动、基本战斗、状态读取、跟随 |
| P2 Agent + MCP | 工具封装、自然语言理解、Agent Loop、任务反馈 |
| P3 合作生存 | 采矿、寻路、合成、物资与分工 |
| P4 完整流程 | 装备成长、复杂探索、Boss 战术、长期协作，尝试推进至月亮领主 |

## 7. 待验证问题

1. 单客户端能否可靠维护完整装备、伤害、死亡与复活机制的 Player？
2. 虚拟 Player 的原生及第三方武器兼容程度？
3. AI 数据如何可靠保存与恢复？
4. 备选双客户端能否稳定后台运行并自动加入？
5. 低延迟控制和地下寻路如何实现？
6. MCP 如何表达持续任务与状态反馈？

## 8. 本轮工作边界

先调查 TerraGuardians、TerraBlind、MoreAIPlayer，给出源码依据、可实现路线和风险。之后再开展最小原型，不在 P0 提前实现 LLM、MCP、自主规划或完整通关。

用户定义体验并决定架构取舍；AI 负责源码调查、方案建议、实现、编译和排障；游戏内验证由用户与 AI 配合。所有结论区分源码已确认、工程推断、未验证。

## 9. 后续多人目标（2026-10-20 补充）

目标规模：2–3 名真人玩家，加上 1 个由 AI 控制的角色，即总计 3–4 个角色。真人各自运行联机所需的客户端；不要求每位真人为 AI 额外启动客户端。AI 是否最终需要独立客户端，仍由技术验证决定。

本目标不进入第一批验收，也不要求等完整通关能力完成才开始。单人角色基础稳定后，单独规划多人可行性验证。

后续必须验证：

- 房主和加入者看到的是同一个 AI，移动、生命值、装备、战斗与死亡状态一致。
- 角色行为有单一控制权威，避免各客户端重复更新、重复执行动作或重复结算伤害。
- 多人发出的指令如何授权、冲突时如何处理，以及紧急停止的权限，进入多人阶段再确定。
- 玩家加入、退出、掉线与重连后不复制角色或物品，不遗留失控动作。
- 房主开服与独立服务器是否均支持，需分别验证，目前不承诺两者已兼容。

对当前设计的约束：区分真人发令者与受控 AI；动作执行入口不固定为 Main.LocalPlayer；全局输入与角色生命周期适配集中管理。第一批仅在单人模式工作，多人环境明确拒绝相关演示操作，不静默尝试生成角色。当前不提前实现网络协议、同步框架或多人指令仲裁。

单客户端方案在单人模式通过，不代表虚拟 Player 能直接通过原生网络协议同步。多人阶段若需要调整角色底座，保留替换底层控制实现的空间，不将首个原型视为最终网络架构。
